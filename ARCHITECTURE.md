# Receivables Control System: Architecture

## Overview

Full-stack financial tracking application for clients, dōTERRA orders, receivables, payments, reporting, and product catalog management. The backend is a stateless JWT-protected REST API; the frontend is a React SPA served by Vite.

## Technology

- Backend: Node.js, Express, Prisma ORM, Zod, JWT, bcryptjs, morgan, multer (ES Modules, `"type": "module"`).
- Frontend: React 18, React Router 6, Vite, Tailwind CSS 3, Flowbite plugin, Recharts, SheetJS, lucide-react, react-icons (brand icons, e.g. WhatsApp/Instagram), react-number-format (ATM-style currency masks via `CurrencyInput`).
- Database: PostgreSQL 15.
- Tests: Vitest, Supertest, React Testing Library, jsdom.
- Code quality: Prettier 3 for formatting; ESLint 9 (flat config, per workspace) for code quality — the two are disjoint by design via `eslint-config-prettier`.
- Local infrastructure: Docker Compose with PostgreSQL and Adminer.

Start the complete environment with:


## Domain Model

- `User` owns `Person` and `Order` records; ownership is enforced in every controller. It also owns a `SaleCounter` (one row per user, `lastNumber`) used to generate the sequential `V-XXXX` sale numbers.
- `Person` stores client data, including WhatsApp, Instagram, address, `birthday` (day/month as `"DD/MM"`, no year), VIP, dōTERRA membership, and team-member flags. The `isTeamMember` flag is purely informational: it marks a client who is part of the user's team (column "Equipe" in the client list) and has no effect on orders or financial tracking — it only feeds the classification filter, sorting, the details modal, and the Excel export. The `isSelf` flag (at most one per user) marks the logged-in user's own record; `POST /api/people/self` gets or creates it (named after the user's `username`). A sale's client is always a non-self person.
- `Order` contains order metadata, status, payment type, notes, an order-level `shippingValue` (frete, `Decimal(10,2)`, default `0`, included in `totalValue`), and nested `Item`/`Payment` records. `orderNumber` is unique per user. `orderType` (`COMPRA`, default, or `VENDA`) distinguishes dōTERRA purchase orders from stock sales; the sales endpoints and UI only operate on `VENDA` rows. Sales additionally carry `deliveredAt` (`DateTime?`, null = not yet delivered) and `additionalValue` (`Decimal(10,2)`, default `0`, extra sale charges summed into `totalValue` and into the `QUITADO` rule together with `shippingValue`). Order-level dōTERRA metadata is stored in `doterraPv` (`Decimal(10,2)` nullable, the PV points of the dōTERRA order), `doterraValue` (`Decimal(10,2)` nullable, the monetary value of the dōTERRA order, informational only — never part of `totalValue`/pending/status), and `attachmentFilename` (nullable, the server-generated UUID filename of the uploaded order screenshot; sales never have attachments). Sales also carry `passesGatewayFeeToClient` (Boolean, default `false`, migration `20260919140000_add_gateway_fee_fields`), recording that the InfinitePay fee was passed on to the client; it is persisted from the payment form (see the payment-gateway fee bullet below).
- `Item` stores a negotiated `chargedValue` plus optional product, member-price, and details snapshots. It also carries a `quantity` (integer ≥ 1, default 1), a `forStock` boolean (the "para meu estoque" toggle, only meaningful for self-person items and required to reference a catalog product), and a `chargedValueMode` enum (`UNIT` — chargedValue is the per-unit price, line total = chargedValue × quantity; `TOTAL` — chargedValue is the full line value). For stock-bound kit items it also carries `kitStockMode` (`KIT` | `COMPONENTS`, the user's choice of what goes to stock) and `kitSnapshot` (a JSON frozen copy of the kit's composition at item creation/registration time). The per-item PV column was removed (migration `20260830100000_add_doterra_fields_and_infinite_pay`); PV is now captured only at the order level via `Order.doterraPv`. Sale items are always product-bound (`productId` required) and have `forStock = false`; the sale client is injected into every item by the controller.
- `Payment` belongs to an order and optionally a person. Payment creation runs in a Prisma transaction and recalculates order status. `payment.paymentType` (nullable enum `PIX` | `BOLETO` | `CARTAO_CREDITO` | `INFINITE_PAY` | `DINHEIRO`, migration `20260919120000_add_dinheiro_payment_type`) records the per-payment form used to receive money — optional on both purchase-order and sale payments ("Não informada" in the UI leaves it null). `payment.netAmount` (`Decimal(10,2)` nullable, migration `20260919140000_add_gateway_fee_fields`) records the net value the user actually received after the payment-gateway fee; `null` means no fee (or not informed), so the net equals `amount`. The fee is **always derived** (`amount - netAmount`) by `backend/src/utils/paymentFee.js` and never persisted; the payment write endpoints reject `netAmount > amount` and include the derived `feeAmount` in their response.
- `Product` is a global catalog record with `ProductStatus` (`ATIVO`, `INDISPONIVEL`, or `INATIVO`) and a `ProductType` (`SIMPLES`, default, or `KIT`).
- `KitComposition` holds the live composition of a `KIT` product: one row per component (`componentProductId`, `quantity` inside the kit), `@@unique([kitProductId, componentProductId])`. Kits contain only `SIMPLES` products (no nested kits), each with a positive quantity, and must have at least one component to be saved. Order items snapshot this composition into `Item.kitSnapshot` at creation time so later kit edits never affect stock control of already-registered orders.
- `ProductPrice` stores historical regular price, member price, PV, and validity intervals.
- `Inventory` stores the current stock balance per user+product (`@@unique([userId, productId])`).
- `StockMovement` records the signed-quantity history (`ENTRADA`/`SAIDA`/`AJUSTE`) for each user+product. It optionally links to the originating `Order` and `Item` via nullable `orderId` / `itemId` (`ON DELETE SET NULL`) so that order-generated movements can be distinguished from manual ones and survive order/item deletion while preserving audit history. Each movement carries an `effectiveDate` (defaults to `now()`) representing the date the entry/exit actually happened, distinct from `createdAt` (insertion time); the history screen shows both columns. Manual movements default to today and are user-editable; movements generated from an order always use the order's `orderDate` (the controller rejects with `400` if that date is missing).
- `FinancialCategory` and `FinancialTransaction` back the finances ledger (migration `20260919150000_add_finances_module`). `FinancialCategory` is per user (`@@unique([userId, type, name])`), with `type` (`FinancialTransactionType`: `RECEITA` | `DESPESA`), `isDefault`, and `active` (soft-deactivation keeps history). `FinancialTransaction` is a single **settled** cash-flow row — `amount` (`Decimal(10,2)`), `description`, `transactionDate` (`DATE`, the settlement date), optional `notes` — carrying `type`, `origin` (`FinancialOrigin`: `VENDA` | `RESGATE_INFINITEPAY` | `PEDIDO_DOTERRA` | `MANUAL`), an optional `categoryId` (`ON DELETE SET NULL`), and nullable `orderId` / unique `paymentId` (both `ON DELETE CASCADE`, so automatic rows are derived data and disappear with their source). Default categories are seeded idempotently per user by `backend/src/utils/financeDefaults.js` (`DEFAULT_CATEGORIES`, the `ORIGIN_CATEGORY_NAMES` origin→category map, and `ensureDefaultCategories`, which uses `createMany` + `skipDuplicates`); registration calls it inside the same Prisma `$transaction` as the user create, and existing users are backfilled with `npm run backfill:finance-categories`. Automatic rows are derived inside the source write transaction by `backend/src/services/financeSyncService.js`: `syncIncomeFromPayment` upserts one income per non-InfinitePay sale payment (keyed by the unique `paymentId`; removes the row when the payment becomes InfinitePay, or the order is not a non-team sale, mirroring `"Venda <orderNumber> — <client>"` against the `"Vendas"` category), and `syncExpenseFromOrder` keeps exactly one `PEDIDO_DOTERRA` expense in sync per non-team purchase order (`amount = doterraValue ?? totalValue`, `transactionDate = orderDate`, category `"Compra de produtos dōTERRA"`, removed when the order becomes a team order). InfinitePay money enters the ledger only through an explicit redemption.

## API Areas

- `/api/auth`: login and self-registration.
- `/api/people`: authenticated client CRUD. `GET /api/people` supports `q` (name/WhatsApp, accent- and case-insensitive via PostgreSQL `unaccent`/`lower`), `classification` (`vip` | `member` | `vip_member` | `team` | `none`, mapped to `isVip`/`isDoterraMember`/`isTeamMember`), `sortBy`, and `sortDir`. `GET /api/people/:id/summary` returns the client's financial summary in integer cents — `ordersCount` (distinct orders containing the person's items, excluding team orders), `totalItemsCents`, `totalPaidCents`, and `totalOpenCents` (clamped at 0; 0 for self persons) — used by the client details modal. `GET /api/people/:id/purchases` returns one row per order item of the person (both order types, excluding team orders): `orderId`, `orderType`, `orderDate`, `name` (`product.name` falling back to the item description), `quantity`, and `totalCents` (`lineValueCents`), sorted by order date desc then product name asc. The client details modal toggles this list under the financial summary (lazy fetch, cached per person); product names navigate to `/orders?detailsOrder=<id>` (opens the order details modal) or `/sales?editSale=<id>` (opens the sale form, existing param).
- `/api/orders`: authenticated **purchase-order** (`orderType COMPRA`) CRUD, payments, per-person balances, and attachment management. `GET /api/orders` supports `q` + `searchField` (`all` | `orderNumber` | `accountOwner` | `orderNotes`, all accent- and case-insensitive via `unaccent`/`lower`), `status` (single or comma-separated), `paymentType`, `sortBy` (including computed `pendingValue` and the DB columns `doterraPv`/`doterraValue`), and `sortDir`. The search term is committed on submit; filter/sort changes refetch server-side. `updateOrder`/`deleteOrder`/item mutations reject `VENDA` rows (`400 use os endpoints de vendas (/api/sales)`). Attachment endpoints (multipart): `POST /api/orders/:id/attachment` (upload/replace, `file` field, PNG/JPEG/WebP, size limit default 10 MB), `GET /api/orders/:id/attachment` (authenticated streaming of the stored image), and `DELETE /api/orders/:id/attachment` (removes file and column). Deleting an order also removes its attachment file. **Sale payments reuse these endpoints unchanged**: `POST /api/orders/:orderId/payments`, `PUT /api/orders/payments/:id`, and `GET /api/orders/:orderId/balance` all work on `VENDA` orders (they are never team orders).
- `/api/sales`: authenticated sale CRUD (orders with `orderType VENDA`). `GET/POST /api/sales`, `GET/PUT/DELETE /api/sales/:id`. Creation validates a non-self `clientPersonId`, requires a catalog product per item, persists each item's `useCashback` cashback-origin flag (default `false`), resolves kit `kitStockMode`/`kitSnapshot`, computes `totalValue = items + shippingValue + additionalValue`, generates the per-user sequential number `V-0001`/`V-0002`… via `SaleCounter` (atomic upsert + retry on `P2002`), and writes **SAIDA** stock movements (reason `Venda V-XXXX`, `effectiveDate = orderDate`) for every sold item (kits expanded via `expandSaleItemToStockProducts`). `GET /api/sales` supports `q` + `searchField` (`all` | `orderNumber` | `client` | `description`), `status` (single/comma-separated), `delivered` (`true`/`false`), and `sortBy` (DB columns plus computed `pendingValue`/`clientName`). `PUT /api/sales/:id` syncs items **by id** (keeping frozen kit snapshots), applies the net per-product stock delta (`delta > 0` → SAIDA, `delta < 0` → ENTRADA) via `computeSaleStockDiff`, and recomputes status; a scalar-only update (client, freight, additional, description, deliveredAt) just recalcs totals/status. `DELETE /api/sales/:id` reverses stock with an ENTRADA per item.
- `/api/finances`: authenticated cash-flow ledger. `GET /api/finances/categories` returns the user's categories (active and inactive), seeding the default set on first access; `POST` creates a custom category (`name` + `type`, trimmed, unique per `[userId, type, name]` → `409` on conflict); `PUT /api/finances/categories/:id` renames and/or activates/deactivates a category (type is immutable); `DELETE` soft-deactivates it (`active = false`), preserving history. All reads/writes are scoped by `userId` — another user's category returns `404`. Service logic lives in `backend/src/services/financeCategoriesService.js`. `GET /api/finances/transactions` returns the full filtered set (no pagination in the MVP) ordered by `transactionDate` then `createdAt` desc, filtered by `type`, `origin`, `categoryId`, inclusive `from`/`to` dates, and `q` (description/notes, case-insensitive); each row includes its `category` and, when linked to a payment, the derived informative `feeAmount`. `POST /api/finances/transactions` creates a **manual** row (forced `origin MANUAL`; `amount > 0`; `categoryId`, when present, must be the user's and match the entry `type`). `PUT`/`DELETE /api/finances/transactions/:id` accept **manual rows only** — automatic rows are rejected with `400` so the user edits the source payment/order instead. `POST /api/finances/settlements` registers an InfinitePay redemption (`orderId` of an owned non-team sale carrying at least one `INFINITE_PAY` payment, `amount > 0`, `transactionDate`, optional `notes`) as a linked `RESGATE_INFINITEPAY` income row (`paymentId` null); partial redemptions may repeat. `GET /api/finances/summary` accepts the same filters and returns `totalIncome`/`totalExpense`/`balance` as fixed two-decimal strings, computed in integer cents over the whole filtered set. Service logic lives in `backend/src/services/financeTransactionsService.js`; automatic derivation from sale payments and dōTERRA orders lives in `backend/src/services/financeSyncService.js` and runs inside the `paymentsService`/`ordersService` transactions (payment create/update and purchase-order create/update/item mutations).
- `/api/products`: catalog CRUD, status/search/sort/pagination, current prices, price history, and the derived `pricePerPv` value (member price divided by PV, rounded to two decimal places). Create/update accept `productType` (`SIMPLES`|`KIT`) and `components` (`[{ componentProductId, quantity }]`); the response includes `productType` and the kit `components` (as `[{ componentProductId, quantity }]`). The CSV catalog loader only creates `SIMPLES` products; kits are composed manually via the UI.
- `/api/stock`: authenticated inventory listing, per-product movement history, movement registration (transactional, signed balance), and `POST /movements/:id` to undo the last movement. `POST /movements` accepts an optional `effectiveDate` (`YYYY-MM-DD`, defaults to server `now()`) and `GET /api/stock` supports `q` (product code/name, accent- and case-insensitive), `sortBy`, and `sortDir`.

## Important Design Decisions

- The backend runs on native ES Modules (`"type": "module"`): source, tests, scripts and seed use `import`/`export`, and relative imports carry the `.js` extension. `__dirname` is derived from `import.meta.url` where needed (`middlewares/upload.js`, `scripts/loadProducts.js`). `dotenv` is loaded conditionally (`NODE_ENV !== 'test'`) in `config.js`/`app.js` so test env vars are not overwritten.
- Code quality is split between **Prettier** (formatting only) and **ESLint 9** (rules only), with per-workspace flat configs (`backend/eslint.config.js`, `frontend/eslint.config.js`) that end with `eslint-config-prettier` so the two never conflict. Backend uses `@eslint/js` recommended + `globals.node`/`globals.vitest`; frontend adds the React/react-hooks/jsx-a11y recommended presets with `globals.browser`/`globals.vitest`. The `react-hooks/set-state-in-effect` rule is off and `react-hooks/refs` is a warning because the existing page-hook effects intentionally load data and keep a latest-callback ref; the `^_` prefix opts unused args/vars/caught-errors out of `no-unused-vars`.
- Financial calculations use integer cents in application code; database monetary fields remain `Decimal(10,2)`.
- HTTP error handling is centralized: services/utils throw errors created by the `backend/src/utils/httpError.js` factories (`badRequest`, `notFound`, `forbidden` — plain `Error`s carrying `.status`; `stockUndoService` attaches `orderNumber`/`orderId` extras to the order-lock rejection), and every controller catch delegates to `backend/src/middlewares/errorResponse.js#handleError`, which maps `ZodError` → 400 `{error: errors}`, `.status` errors → that status with `{error: message}` (+ extras), and anything else → the fallback (500, or 400 for payments/stock) with a generic message. The Prisma client is a single instance exported from `backend/src/config/database.js`, reused by every controller and service.
- Product `pricePerPv` is calculated at API projection time using integer/`BigInt` arithmetic and half-up rounding; it is not persisted. Products can be sorted by this derived value.
- The PostgreSQL `unaccent` extension (enabled by migration `20260821180000_enable_unaccent_extension`) is used by the shared `backend/src/utils/search.js` helper for `q` text searches on `/api/people`, `/api/orders` and `/api/stock`, so that accented and unaccented terms match interchangeably (e.g. `"Cássia"` matches `"cassia"`). The helper escapes LIKE wildcards (`%`, `_`, `\`) and combines with the existing userId/filters via a Prisma `id IN (...)` clause.
- The frontend loads the product catalog once with `pageSize=all`; search, status filtering, sorting, and infinite-scroll slicing are client-side.
- Clients (`/people`) and Stock (`/stock`) follow the same client-side pattern: fetch the full list and filter/sort in memory as the user types. Orders (`/orders`) is server-side: the search term is submitted on Enter/button and filters + sort trigger a `GET /api/orders` refetch with all params combined (filters and sorting applied together), with an `AbortController` cancelling in-flight requests on rapid changes.
- Sortable table headers (`SortableHeader`) and the search input (`SearchInput`) are shared `src/components/` widgets; column headers toggle asc/desc with an `aria-sort` indicator.
- Products with `ATIVO` or `INDISPONIVEL` status can be selected for orders; `INATIVO` products cannot be newly selected.
- The catalog loader is an idempotent diff and preserves manual `INDISPONIVEL` status.
- Responsive tables keep semantic table markup and use Flowbite's Tailwind-only `data-label` card pattern below `md`.
- `ActionMenu` is the shared kebab menu for row actions. Menu panels use `z-[80]`.
- The frontend uses a Vite `/api` proxy, avoiding browser-side localhost/CORS issues on local networks.
- Complex pages follow a "page-as-orchestrator" architecture: each page lives in `pages/{Nome}/` with `index.jsx` (≈60–150 lines), a `use{Nome}.js` custom hook owning state, API calls, and mutation handlers, local `components/` for subcomponents, and `utils/` for pure helpers. The original `*Page.jsx` file is a one-line shim (`export { default } from './{Nome}/index.jsx';`) so existing imports keep working. See `frontend/docs/frontend-architecture-guide.md` for the progressive complexity policy and the page-refactoring playbook.
- **Finances page** (`pages/Finances/`, route `/finances`, nav item "Finanças"): the level-3 ledger screen. `useFinances` owns the filtered list + period summary (type/origin/category/period selects refetch immediately in place, while the free-text term is committed only on submit), the manual create/edit form and the delete confirmation; `useFinanceCategories` owns category management; `useSaleSettlements` owns the InfinitePay redemption flow reused by the Sales page. Manual rows are the only editable/deletable ones in the table (automatic rows show a link back to the originating sale/order instead); the derived gateway fee is shown as informative text only. The ledger summary flips between the integer-cent totals returned by `GET /api/finances/summary`. The Sales page exposes "Registrar resgate InfinitePay" for sales carrying an `INFINITE_PAY` payment, opening `GatewaySettlementModal` (see `useSaleSettlements`).
- **No dashboard / index redirect**: the legacy dashboard page and the `/api/dashboard` endpoints were removed (Phase F7). The app index (`/`) now redirects to `/finances`, which is the landing screen; future reports will replace the dashboard. `frontend/src/utils/exportExcel.js` is kept dormant for those reports.
- Stock movements are signed (`ENTRADA` `+q`, `SAIDA` `-q` forbidding negative stock, `AJUSTE` absolute target with signed delta); `registerMovement` and `undoLastMovement` each run in a single Prisma transaction.
- Only the **last** movement of a product can be undone (enforced by counting movements with a greater `createdAt`); undoing the only movement deletes the `Inventory` row so the product leaves the stock list and becomes available for a fresh initialization.
- **Order ↔ Stock integration**: when an order contains a self-person item flagged `forStock` with a catalog product, the orders domain (`ordersService` via `orderStockIntegration`) automatically creates an `ENTRADA` `StockMovement` (quantity = `item.quantity`, reason `Pedido <orderNumber>`) inside the same Prisma transaction as the order/item mutation. On `updateOrder`, `addItemToOrder`, `updateItem`, `deleteItem`, and `deleteOrder`, the service computes the net per-product stock delta (via the pure `computeStockDiff` helper in `backend/src/utils/stockDiff.js`) and applies `ENTRADA`/`SAIDA` movements tied to `orderId`. All mutations now run in a Prisma `$transaction`, and stock reversals are blocked with `400 Insufficient stock` (with an orientative message pointing to the Estoque page) when the current inventory cannot cover the deduction, preserving the never-negative rule. The canonical movement logic is extracted into `backend/src/services/stockService.js` (`applyMovement(client, ...)`), which `StockController.registerMovement`, `ordersService`, and `salesService` call. Every order-generated movement records `effectiveDate = order.orderDate` (the service guards with `400 Data do pedido é obrigatória para movimentações de estoque` if the order date is missing). **Movements generated by an order (`orderId != null`) cannot be undone via the stock endpoint** (`POST /api/stock/movements/:id/undo` rejects with `400` + `orderNumber`/`orderId`); reversal is driven exclusively by editing/removing the item in the order. The frontend hides the undo button in this case and instead shows an info card with the order number and a "Ver pedido" deep-link to `/orders?editOrder=<id>` (auto-opens the edit modal).
- **Kit products and stock**: a `KIT` product is priced manually (own `regularPrice`/`memberPrice`/`pv`); its composition lives in `KitComposition`. When a self-person item referencing a kit is flagged `forStock`, the user must choose a `kitStockMode`: `KIT` stocks the kit product as a single unit, `COMPONENTS` stocks every component scaled by the kit quantity (`componentQty × item.quantity`). The shared helpers in `backend/src/utils/kitStock.js` — `resolveKitSnapshot(client, productId)` and `expandItemToStockProducts(item)` — expand an item into its effective `[{ productId, quantity }]` stock effect; `computeStockDiff` uses this expansion so quantity changes and mode switches (`KIT` ↔ `COMPONENTS`) produce the correct minimal `ENTRADA`/`SAIDA` movements automatically. The kit composition is **frozen** into `Item.kitSnapshot` when the item is created (or when its product changes); later edits to a kit never affect stock control of already-registered orders, even when their items are edited (requirement 5). `updateOrder` was refactored from a destructive `deleteMany`+`create` to a **sync-by-id** flow: the frontend sends the existing item `id` (UUID) for kept items, the controller updates them (preserving `kitSnapshot`), creates new ones, and deletes removed ones — this is what keeps frozen snapshots and stock history links intact across order edits.
- **Per-item quantity and price mode**: every `Item` carries `quantity` and `chargedValueMode` (`UNIT`|`TOTAL`). Financial math uses the `lineValueCents(item)` helper (in `backend/src/utils/money.js` and mirrored on the frontend) which returns `toCents(chargedValue) * quantity` in `UNIT` mode or just `toCents(chargedValue)` in `TOTAL` mode. This is used in `computeOrderStatus`, order `totalValue` computation, payment balance/item totals, and frontend `getOrderSelfCents` / order-form `calculateTotal`. Existing items (qty=1, UNIT) are fully backward-compatible.
- **Order shipping (frete)**: `Order.shippingValue` (migration `20260823100000_add_order_shipping_value`) is an order-level cost, default `0`, included in `totalValue` and therefore in pending balances and the payment flow. `computeOrderStatus` takes an optional `shippingCents`: once every per-person balance is settled, an order with chargeable non-self items only reaches `QUITADO` when the sum of payments also covers `non-self items + shipping`; self-only and gift-only orders are not blocked by shipping. The displayed pending (`getOrderSelfShippingCents` in `frontend/src/pages/Orders/utils/receivablesHelpers.js`, mirrored by the server-side `pendingValue` sort in `backend/src/utils/ordersSort.js`) treats the frete as the user's own cost when no item is bound to another person — current-version orders are all-self and display R$ 0,00, while legacy orders that linked people to items keep the frete collectable (it was prorated into their item values at creation time). The order form shows an editable **Frete (R$)** input in a bottom summary block (testid `order-freight`) placed after the items list and before the submit buttons, alongside a read-only **Valor Total** (products + frete, testid `order-totals-charged-footer`); the former top summary block was removed. The payment and details modals display a **Frete** row (`order-summary-shipping` / `details-summary-shipping`).
- **Order-level dōTERRA fields and attachments**: `Order.doterraPv` and `Order.doterraValue` (migration `20260830100000_add_doterra_fields_and_infinite_pay`) are user-filled, nullable order-level fields representing the PV and the monetary value of the dōTERRA order. `doterraValue` is informational only: it never enters `totalValue`, pending balances, or order status. The per-item `Item.pv` column was removed; the old computed `totalPv` sort and the "PV Total"/"Soma dos PV" UI were replaced by the order-level `doterraPv` column (sortable via the DB column). Order attachments are stored on disk under `backend/uploads/orders/` (gitignored; `ATTACHMENTS_DIR` env override for tests), with a server-generated UUID filename and a whitelisted extension (PNG/JPEG/WebP) so path resolution never uses client input. Uploads go through `multer` (`backend/src/middlewares/upload.js`), size is validated per-request (`ATTACHMENT_MAX_BYTES`, default 10 MB), and every read goes through the authenticated `GET /api/orders/:id/attachment` endpoint; the frontend fetches the image as a blob and shows it in a read-only modal, so no system folder is ever exposed. Because `docker-compose.yml` bind-mounts `./backend:/app`, files persist on the host both under Docker and `npm run dev`.
- Items assigned to a self person (`Person.isSelf`) are treated as **already received**: their value never contributes to pending balances (per-person or order-level), and they never block an order from reaching `QUITADO`. No `Payment` record is created for them. The shared helper `backend/src/utils/receivables.js` (`computeOrderStatus`, `personPendingCents`, `syncOrderStatusesForPersons`) centralizes this rule; order status is now recomputed on order/item create/update/delete and when a person's `isSelf` flag toggles. The order form's person select — rendered only for team orders, since non-team items belong to the user without a visible person field — always offers the user as an "Eu (você)" option (auto-creating the self person via `POST /api/people/self` on first selection), and the "Esta pessoa sou eu" checkbox in the People form consolidates/transfers the flag.
- **Team orders**: an `Order` flagged `isTeamOrder` (migration `20260824164617_add_team_order`) records an order that another team member placed **and paid for** themselves. It carries the usual order metadata and items (for reference) but is excluded from the user's financial tracking: it is never `PENDENTE`/`PARCIAL`/`QUITADO` — `computeOrderStatus` returns the dedicated `EQUIPE` status whenever `isTeamOrder` is true — and it never generates stock movements, never accepts payments (the API rejects `POST /api/orders/:id/payments` on team orders), and it generates no financial-ledger entry (`financeSyncService` skips team orders), so it contributes to neither the finances summary nor the order balances. In the UI the toggle "Pedido da equipe" shows a notice and hides the per-item "para meu estoque" option and the payment action is hidden; the orders table omits the `Status`/`Valor Pendente` columns and the status filter was removed (team orders are identified by the absence of the payment action), and a team order can be toggled back to a normal order, which recomputes to the appropriate standard status. The client of a team order is chosen at the **order level**: a `Cliente` select below the team toggle binds the chosen person to every item, replacing the previous per-item "Pessoa" select. It is still persisted on `Item.personId` — the same storage the self person uses for regular orders — so no schema change was needed. Legacy team orders whose items have divergent persons keep the per-item selects; when every item already shares the same person (or none) the form hydrates the order-level client instead. Unifying a legacy order under a single client asks for confirmation in a `ConfirmDialog`, and the orders table shows the derived client (single name, `Vários` for divergent items, `Eu (você)` for regular orders) in a new `Cliente` column right after `Conta ID`.
- The "Adicionar Estoque" product selector is filtered client-side (`availableProducts`) from the catalog loaded lazily on dialog open (`GET /products?pageSize=all`) minus the products already in the user's inventory, regardless of product status.
- **Sales (pedidos de venda)**: a sale records products sold from the user's own stock to a client (`Order.orderType = 'VENDA'`), with a sequential `V-XXXX` number per user generated atomically from `SaleCounter`. Sales use the same status transitions (`PENDENTE` → `PARCIAL` → `QUITADO`), but `computeOrderStatus` now also accepts `additionalCents` so `QUITADO` requires payments ≥ items + freight + additional. The client is selected at the sale level (`clientPersonId`, non-self) and injected into every item by the controller, so the payment/balance flow always has exactly one person. Because the client is always non-self, the per-person balance returned by `GET /api/orders/:id/balance` for a `VENDA` includes the order-level freight and additional charges in that client's `pending` (spread proportionally across non-self persons by `buildOrderBalances` in `backend/src/utils/orderBalances.js`), while `itemTotal` remains the sum of the items only; purchase orders keep their previous balance behavior. Stock semantics are **inverted** compared to purchases: creating a sale writes a `SAIDA` movement per item (kits expanded via `expandSaleItemToStockProducts`, which forces `forStock: true`), editing applies the net delta via `computeSaleStockDiff` (`computeStockDiff` without the person/`forStock` filter), and deleting restores stock with `ENTRADA`. Insufficient stock blocks creation/update with `400 Estoque insuficiente para {nome}: disponível X, necessário Y`. Sale items are always product-bound and the kit `kitStockMode` is mandatory for KIT products; unchanged items keep their frozen `kitSnapshot` (sync-by-id, same contract as `updateOrder`). Sales never have attachments, never have `isTeamOrder`, and are excluded from purchase-order endpoints (`GET /api/orders` filters `orderType COMPRA`; the other order/item mutations return `400` for `VENDA` rows).
- **Per-payment payment type**: `Payment.paymentType` (migration `20260830181046_add_sale_orders_and_payment_type`, later extended with `DINHEIRO`) records how each individual receipt was received (`PIX` | `BOLETO` | `CARTAO_CREDITO` | `INFINITE_PAY` | `DINHEIRO`, optional, null = "Não informada"). The payment and edit-payment modals of both Orders and Sales show a "Forma de Pagamento" select, and the details modals render a `PaymentTypeBadge` per payment (`payment-badge-<id>`). The Sales screen limits its select to `PIX`, `INFINITE_PAY` and `DINHEIRO` via `PAYMENT_TYPE_OPTIONS` (`frontend/src/pages/Sales/utils/saleHelpers.js`); the edit modal still exposes a legacy type (e.g. `BOLETO`) when the payment being edited already carries one. The shared `paymentPayload`/`editPaymentPayload` helpers in `frontend/src/pages/Orders/utils/receivablesHelpers.js` carry `paymentType` (create omits it when empty; edit always sends it, with `''` mapped to `null` so a previously-set type can be cleared). `Order.paymentType` remains the purchase-only "como paguei à dōTERRA" field.
- **Payment-gateway fee (InfinitePay)**: when a payment write sends `passesGatewayFeeToClient` (optional boolean), `paymentsService` persists it on the order inside the same transaction; omitted values leave the order flag unchanged. The Sales payment and edit-payment modals show, **only for `INFINITE_PAY`**, a "Repassar taxa do InfinitePay ao cliente" checkbox and a "Valor líquido recebido (R$)" field (`salePaymentNetAmount` / `saleEditPaymentNetAmount`), with the derived fee displayed live. The overpayment guard compares the **net received** (falling back to the charged amount) against the pending balance, so a fee passed on to the client (`amount > pending`, `net == pending`) does not trigger the confirmation dialog; the balance still settles by `amount` with pending clamped at zero, so it never produces credit. The details modal renders `Taxa` and `Líquido` per payment (`payment-fee-<id>`), and `frontend/src/utils/paymentFee.js` mirrors the backend fee helpers.
- **Sales UI**: a dedicated **Vendas** menu entry (`/sales`) renders a Level 3 page (`src/pages/Sales/` with `useSales`, `useSaleFilters`, `useSalePayments`, components and `utils/saleHelpers.js`) mirroring the Orders structure. The form has Cliente (non-self select), Data do Pedido, Frete, Valores Adicionais, Descrição and optional Data de entrega, plus per-item product/quantity/UNIT-TOTAL/detalhes (with KIT `kitStockMode` radios and a "O produto teve origem no cashback de 70%" checkbox that reveals a read-only member total with 70% off; `chargedValue` is never prefilled); it omits all purchase-only fields. The table shows Data, Cliente (hover tooltip listing each product with its charged line total), Valor, Pendente, Recebido (paid total colored red/green/blue for underpaid/settled/overpaid), Entrega badge ("Pendente de entrega" / "Entregue + data"), Descrição (single-line truncation with the full text on hover), Status and Ações (Registrar Pagamento / Dar baixa, Detalhar Pagamentos, Marcar como entregue / Desmarcar entrega, Editar, Excluir). Delivery toggles via a scalar `PUT /api/sales/:id` (`deliveredAt: today` to mark, `null` to unmark). Payments reuse the `/orders` payment endpoints with a fixed client. Because a sale has a single client, the details modal lists the items and the received payments directly (no per-person accordion, unlike Orders) and emphasizes the pending value in the header. Deep-link `/sales?editSale=<id>` (from the stock history) auto-opens the edit modal.
- **Sales in stock history and Excel**: stock history movements linked to a sale show a `Venda V-XXXX` badge and a "Ver venda" locked-notice button that navigates to `/sales?editSale=<id>` (purchase orders keep `Pedido #X` / `/orders?editOrder=<id>`), decided by `movement.order.orderType`. The Excel export (`exportExcel`) gained a `sales` input: a new **Vendas** sheet (Número, Data, Cliente, Valor Total, Taxa, Líquido, Status) and the **Histórico de Pagamentos** sheet now consolidates payments from both purchases and sales, with **Taxa (R$)** and **Valor Líquido (R$)** columns derived per payment. With the dashboard removed (Phase F7), `frontend/src/utils/exportExcel.js` and its test are kept **dormant** for future reports — the utility has no caller in `src/`.

## Frontend Design System

- **Semantic tokens over raw colors.** The palette lives in `frontend/src/index.css` as CSS variables (`:root` = light, `.dark` = dark) and is exposed to Tailwind via `frontend/tailwind.config.js`: surfaces `base`/`surface`/`elevated`, `line` for borders, text tiers `ink`/`ink-soft`/`ink-faint`, the accent family `accent`/`accent-hover`/`accent-soft`/`accent-on`/`accent-on-soft`, the support palette `success`/`warning`/`info`/`mystic`/`danger` (each `*-soft` background + `*-fg` text), and the payment badges `badge.boleto`/`badge.infinitepay`/`badge.pix`. Components consume `bg-surface`, `text-ink`, `bg-accent`, `bg-success-soft`, `text-danger-fg`, etc. — never `gray-*`/`blue-*`/`primary-*` or hex literals for theme/status colors.
- **Pink is signal, not wallpaper.** The accent (`#D6336C` light / `#FF79C6` dark, Dracula-inspired) is reserved for primary actions, links, the active navigation item, focus rings and progress/selection indicators. Badges and statuses draw from the secondary palette, and table row hover uses `accent-soft`.
- **Light/dark modes.** Dark mode follows Dracula-ish neutrals (`#1E1F29` background, `#282A36` surface, `#44475A` border, `#F8F8F2` text). `ThemeContext` toggles the `dark` class on `<html>` using `localStorage['theme']` with a `prefers-color-scheme` fallback, and the pre-render IIFE in `main.jsx` avoids a flash. Because tokens resolve per mode, tokenized elements no longer need `dark:` variants.
- **Central badge mapping.** `frontend/src/utils/badgeStyles.js` is the single source for order-status, payment-type, delivery, product-status, movement, stock-quantity and boolean badge color classes; domain components import the maps instead of duplicating class strings.
- **Accessibility.** `frontend/scripts/contrast-check.mjs` validates every token text/background pair against WCAG AA (≥ 4.5:1) in both modes (`node scripts/contrast-check.mjs`); re-run it after changing a token value.
